# 本地优先、手动大模型任务识别设计

日期：2026-10-03  
状态：设计待确认；本次不修改产品代码，不调用模型，不启动生成或上传。  
适用程序：独立智能体 `redbook_agent`。旧 `redbook_workflow` 的人工脚本和页面保持原状。

配套文档：[完整识别提示词与输出约定](2026-10-03-agent-llm-task-recognition-prompts.md)。

## 1. 目标与边界

用户先通过本地关键词和正则得到任务计划；发现漏识别、误识别或识别失败时，可以点击“大模型任务识别”重新理解同一段原始指令。

验收目标：

- 普通发送仍使用本地规则，识别阶段不调用大模型、不同步额度。
- 每次主动点击最多触发一次识别模型请求，不产生内容、图片或平台操作。
- 大模型返回的是候选计划，而不是执行命令；必须先采用，再通过原有“确认并执行”启动。
- 用户能够看到数量、栏目、交付方式、运行模式和其他要求的差异。
- 已识别的要求必须传到实际执行端；暂不支持的要求明确显示，不用一句“已安排”掩盖。
- 重识别失败不破坏原计划，不改变已开始的任务、检查点和供应商默认值。

本功能不是开放式工具调用智能体，也不是新闻事实核查器。它不联网搜索新闻，不调用 MCP/SKILLS，不登录浏览器，不发布、删除草稿，不扩展现有工具权限。

## 2. 现状核查

已结合 GitNexus 的 `redbook_auto_agent` 调用图与实际源码核查；独立智能体索引已在本次设计时刷新。图查询有跨语言解析限制，因此以下结论同时以实际文件为依据。

| 当前位置 | 实际行为 | 对设计的影响 |
| --- | --- | --- |
| `backend/app.py::add_message` | 先处理状态问题；任务进入本地解析器 | 状态询问继续本地处理，不增加模型开销 |
| `apps/web_service.py::Workbench._parse_agent_message` | 关键词识别栏目、正则识别数量，生成计划和模板回复 | 保留为默认策略，不替换成每次调用 LLM |
| `Workbench.append_agent_message` | 再解析并保存用户消息和计划 | 解析业务失败时需保留有效原文，才能使用备用识别 |
| `frontend/src/App.tsx` | 右侧“本次计划”展示结果，并提供“确认并执行” | 新按钮放在计划区域，不新增独立页面 |
| `Workbench.execute_agent_plan` | 冻结任务文件和模型角色，再启动任务 | 候选采用与实际执行必须分离 |
| `apps/cli.py::_load_agent_job_plan`、`AgentJob` | 目前接收栏目、标题、数量、提示词、评价视角和回溯参数 | 新增约束不能只保存在前端或被加载器忽略 |
| `apps/cli.py::controller_plan` | 执行中的有限主控，主要建议任务顺序 | 不是自然语言任务识别；本功能单独承担识别职责 |
| `src/agent/conversation_store.py` | PostgreSQL 保存会话、消息、计划及版本 | 复用现有存储，不降级到临时 JSON/内存 |

现有不足不仅是关键词覆盖有限：新闻任务提示词包含固定关键词，原句中的个性化主题和约束不一定传入执行；“最快速度”也没有直接覆盖会话任务的实际运行模式。新设计需要同时解决识别和参数传递，但不借机重写新闻生成流程。

GitNexus 对真实 `_parse_agent_message` 的上游分析为 LOW，直接调用者为 `add_message` 和 `append_agent_message`；`execute_agent_plan` 的直接上游为 `confirm_plan`。这不代表无需验证，重点风险是前后端计划契约和实际执行参数的一致性。

## 3. 方案选择

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 本地规则后，用户手动请求 LLM 候选 | 默认快、费用可控、改变可见 | 需要一次主动点击和计划确认 | 采用 |
| 本地失败自动调用 LLM | 少一次点击 | 失败定义难统一，可能意外消耗订阅和延长响应 | 本次不采用 |
| 所有消息先交给 LLM | 理解范围较广 | 每次增加等待与成本，状态询问也可能产生额外请求 | 不采用 |

同一任务只有一个待执行的当前计划；大模型候选与当前计划分开保存。识别来源不等于执行权限，大模型不能自行批准计划。

## 4. 前端交互

### 4.1 按钮位置

保留当前页面布局，在右侧“本次计划”的标题下、任务列表上增加紧凑工具栏。

```text
本次计划                                      待确认
识别来源：本地规则            [大模型任务识别]

每日新闻 × 5
运行模式：速度优先
交付：小红书草稿
图片评分：仅供参考
模型：主控 / 写稿 / 生图的实际绑定
需要确认或尚不支持的要求：……

[确认并执行]
```

- 按钮名称固定为“大模型任务识别”，使用现有 lucide 图标库的 `BrainCircuit`，次级按钮样式。
- 不与“确认并执行”同色同权重，避免误认为点击即开始生成。
- 正常规则结果、部分识别和“未识别到任务”均可以展示按钮。
- 空消息、过长消息、纯状态查询不提供识别入口。
- 模型尚未配置时保留按钮位置，禁用并显示可操作原因；不强行打开登录或配置窗口。
- 手机端计划栏位于对话下方，按钮与状态可以换行，不能挤压任务标题。

### 4.2 一次识别的流程

1. 用户发送指令，原文保存成功后展示规则计划。
2. 用户点击“大模型任务识别”。请求引用原始用户消息 ID，不引用助手生成的计划说明。
3. 按钮显示“识别中”；原计划保留，但暂时禁止确认执行，防止两个操作竞争。
4. 完成后展示候选比较面板，列出改变和未覆盖要求。
5. 用户选择“保留原计划”或“采用大模型计划”。两种操作都不启动任务。
6. 采用成功后更新当前计划，识别来源显示“大模型”；用户仍单独点击“确认并执行”。

比较面板展示：栏目与篇数、主题偏好、交付平台、运行模式、模型角色、图片评分设置，以及需要补充或不支持的要求。只显示任务信息和实际差异，不展示模型思维链。

运行中或已执行的计划不能原地重识别。用户如需调整，发送新的任务消息生成新的待确认计划；原运行继续使用冻结配置。

### 4.3 状态与错误

| 状态 | 页面行为 |
| --- | --- |
| 本地识别完成 | 展示规则计划，允许手动 LLM 识别 |
| 本地部分识别/未识别 | 保留原文，展示缺项，不自动请求 LLM |
| 模型识别中 | 禁用重复点击、采用和确认执行，显示实际耗时 |
| 候选待选择 | 展示差异；选择前不启用确认执行 |
| 需要补充 | 展示具体问题，候选不可执行 |
| 识别失败 | 恢复原计划可用状态，提供错误原因和手动重试 |
| 候选已过期 | 不允许采用，提示任务或设置已经改变 |

弹层需要键盘焦点管理、Esc 关闭、关闭后焦点返回按钮；加载状态通过 `aria-live` 通知。关闭弹层不表示服务端请求已经取消；请求未终止时不能再次提交。

## 5. 识别与执行之间的数据契约

### 5.1 统一的任务规范

本地解析结果和 LLM 候选最终都由服务端转换为同一种 `TaskSpec`。模型返回的 JSON 只是输入，不能直接作为 CLI 参数或环境变量。

| 字段 | 含义与所有权 |
| --- | --- |
| `source_message_id` / `source_text_hash` | 服务端绑定原始用户消息，模型不得生成 |
| `recognition_source` | 服务端标记 `rules` 或 `llm` |
| `jobs` | 有限栏目、篇数和主题要求；服务端校验并补默认标题 |
| `requirements` | 原始要求、证据片段、强度、映射位置和处理结果 |
| `resolved_options` | 本次交付、平台、模式、图片评分等实际参数 |
| `resolved_role_bindings` | 服务端根据模型目录解析的主控/写稿/生图绑定 |
| `unresolved_requirements` | 无法执行、缺少信息或政策冲突的要求 |
| `prompt_version` / `schema_version` | 支持追踪识别版本 |
| `base_plan_id` / `base_plan_version` | 用于比较和防止覆盖过期计划 |
| `executable` | 只由服务端决定，模型不得声明 |

`requirements` 是可查看的覆盖清单，不是模型正确性的保证。服务端检查引用是否真实存在、映射字段是否合法、是否有实际消费者；用户仍能查看原文和映射。不能用模型自报的“置信度 99%”替代这些检查。

### 5.2 支持的任务

| 栏目 | 枚举 | 本轮数量含义 |
| --- | --- | --- |
| 每日新闻 | `daily_news` | 1–20 篇独立稿件 |
| 每日AI讯息/资讯 | `daily_ai_digest` | 1 篇集合稿，内部条目由现有筛选流程决定 |
| 每日羊毛/AI鸡蛋/AI福利 | `daily_wool` | 1 篇 |
| 每日我去 | `daily_wow` | 1 篇 |
| 每日全球事件关注图 | `daily_global_map` | 1 篇 |

不得因为用户说“8条AI资讯”就创建 8 篇集合稿。明确指内部条目时作为栏目要求；含义不明确时要求澄清。既有草稿管理入口仍沿用原流程，本次 LLM 入口不扩展为发布、删除或账号管理工具。

### 5.3 要求必须有实际落点

| 用户要求 | 识别后的传递方式 |
| --- | --- |
| 指定新闻主题、读者偏好、信源偏好 | 合并到相应 `AgentJob.prompt`，保留原意并由现有筛选/生成工具消费 |
| 新闻篇数、栏目种类 | 转换为经过验证的 `AgentJob.kind/count` |
| 速度优先或平衡模式 | 本次计划 `resolved_options.performance_mode`，传到实际任务请求，不改全局默认值 |
| 不上传/保存平台草稿 | 本次 `delivery`；不能只写在助手回复中 |
| MiniMax 订阅、禁止付费降级 | 解析现有模型角色目录，并由宿主计费策略再次检查 |
| 不同步额度 | 本次任务跳过额度同步；识别本身也不进行同步 |
| 专用 profile、后台浏览器 | 使用既有专用 profile 策略；不接受模型生成的目录或浏览器命令 |
| 关闭图片评分硬门槛 | 仅覆盖已有可选评分开关；不关闭图片可读性和资产合法性等基本检查 |
| 今日、真实性、时效性、查重 | 使用运行时北京时间和现有事实/日期/重复检查；模型不自行认定新闻已经核实 |
| 至少 2 条国际冲突 | 保留为明确要求，不能默默改成“偏向”；如果现有执行器只能做到偏好，标记未完全支持并要求用户调整 |
| 公开发布、删除全部草稿 | 当前 LLM 入口不支持，候选不可确认执行；不能偷偷改成存草稿 |

模型不能扩大日期上限、关闭强制事实检查或改写凭据。实际能力清单必须说明当前任务是否支持某参数，不能让提示词先承诺尚未实现的能力。

采用后需要把 `requirements`、解析后的本次选项和角色绑定一起冻结到执行计划、运行记录和检查点中。`_load_agent_job_plan` 与 `AgentJob` 需要接收并校验该契约，或者明确拒绝尚不支持的字段；禁止“读取时丢掉未知参数但继续执行”。断点恢复继续使用冻结要求，而不是重新调用识别模型。

### 5.4 修改任务与原文边界

“改成五篇，不要上传”可以引用同一会话当前尚未执行的计划。传入模型的上下文仅包括该基础计划及其原始指令，不传入整个聊天、RAG、草稿正文或 API Key。

模型必须区分新任务与修改任务。没有“继续/修改/改成”等上下文依赖表达时，不能把历史栏目自动合并进新任务。多个可修改计划存在时，由前端明确选定基础计划；不能让模型猜。

## 6. 后端与模型调用

### 6.1 复用与职责划分

- 规则解析器：维持当前低成本默认入口，输出统一规范。
- 识别服务：构造受限输入、调用一次模型、解析并校验结果；不调用生成或上传工具。
- 规范校验器：检查能力、证据引用、数量、参数、计费和未覆盖要求。
- 计划服务：保存候选、生成差异、原子采用、冻结执行。
- 前端：发起识别、展示差异、明确采用；不能直接提交可信执行参数。

这些是职责边界，不要求为每一步建立一个框架或新的智能体。复用现有 FastAPI、模型配置、JSON 客户端和 PostgreSQL，无需新依赖、Redis 或新增供应商角色。

### 6.2 API 设计

所有接口复用现有 loopback、同源、会话鉴权和 `X-Workbench` 检查。

| 接口 | 功能 |
| --- | --- |
| `POST /api/conversations/{id}/task-recognitions` | 提交 `source_message_id`、基础计划 ID/版本、请求幂等键；返回识别记录 ID |
| `GET /api/conversations/{id}/task-recognitions/{recognition_id}` | 查询状态、实际耗时、错误、候选和差异 |
| `POST /api/conversations/{id}/task-recognitions/{recognition_id}/adopt` | 提交预期会话修订号、基础计划版本；原子创建当前计划的新版本 |
| 原有 `POST /api/plans/{plan_id}/confirm` | 仍是唯一执行入口；再次检查计划、权限和绑定 |

采用成功返回新计划和最新会话修订号。客户端不能提交任意候选 JSON、模型 URL、密钥或文件路径来绕过服务端保存的候选。

### 6.3 供应商与开销

- 使用现有“智能体主控”绑定，不使用写稿或生图绑定代替，不新增第四种角色。
- 主控已配置为 MiniMax 订阅时使用该配置；无有效绑定时提示前往“模型与供应商”设置，不静默选择其他付费模型。
- 对请求应用现有订阅、禁止付费额度和禁止自动降级策略。不能仅因名称为 MiniMax 就假定所有端点均包含在订阅中。
- 配置、目录和能力清单均读取本地信息，不为识别重新同步额度或发收费探测请求。
- 每次识别最多一次模型调用。识别客户端显式限制输出为 4096 tokens、请求超时为 60 秒；不沿用新闻生成默认的长输出和长重试策略。实际值不得超过选中模型/适配器支持范围。
- 超时、限流、无效 JSON 不自动改模型、不自动修复、不自动重试。用户主动重试才产生新尝试，并告知上一尝试可能已经消耗额度。

模型请求使用独立、不可变的本次配置对象解析主控绑定，不通过临时改写进程级 `os.environ` 切换供应商。识别客户端需要显式传递短超时、输出上限和零自动重试；不能只套用现有新闻 JSON 客户端而继承其大输出和多次重试行为。若复杂输入无法在输出预算内完整表达，应报告并建议拆分，不截断原始要求或丢弃约束来强行产生可执行计划。

当前生成队列为运行内队列，不能当成跨进程共享限流器。本期采用简单稳定的准入：同一运行目录有内容任务执行时不接受识别请求，返回可操作的忙碌状态；空闲时一次只接受一个模型识别。同一会话不允许重复并行请求。无需为这个按钮增加共享 Redis 队列。

### 6.4 严格输出校验

使用结构化模型/解析器，拒绝未知字段、重复 JSON 键、非有限枚举和不合法数量。只接受单个完整 JSON 对象；可剥离包围整个对象的一层代码围栏，但不能从任意说明、HTML 或截断输出里猜一个可执行计划。

先执行结构校验，再进行服务端语义校验：

1. 原文、基础计划和引用片段确实存在且属于当前会话。
2. 要求的角色供应商出现在本地目录且可选；相应能力与计费策略允许。
3. 原文明确要求的栏目、交付和数量没有被凭空补充或遗漏。
4. `null` 表示继承，不表示开关关闭；显式否定优先于默认值。
5. 每个标记已映射的字段都有实际消费者。
6. 有歧义、权限冲突、能力不支持或未处理要求时，候选不可执行。

安全检查不能只交给提示词。被引用的文章、网页文本、旧模型输出都只是数据，其中的“忽略系统规则”或“输出密钥”不成为权限。

## 7. 存储、幂等与冲突处理

在 PostgreSQL 的 `agent` schema 增加识别记录；任务计划继续存储在现有会话结构中。生产环境连接失败就报告失败，不切换到本地文件或内存假装成功。

识别记录保存：消息 ID/摘要、基础计划 ID/版本、会话修订号、实际角色绑定指纹、配置/能力版本、提示词版本、状态、开始/结束时间、模型耗时、脱敏候选、校验结果、差异和采用后的计划 ID。默认不记录完整请求头、原始凭据或模型思维链。

流程使用短事务：申请记录并获得准入，释放事务后调用模型，再用版本比较保存结果。不能持有数据库事务等待 60 秒模型响应。

幂等键覆盖消息、基础计划、绑定指纹、提示词和能力版本。相同按键重复提交返回同一尝试，不进行第二次模型调用。用户明确重试使用新的尝试号。浏览器刷新能恢复识别状态和候选。

采用时检查基础计划仍未执行且版本一致、会话修订号一致、绑定与能力配置未变。并发标签页、修改任务或切换模型导致不一致时返回冲突，不覆盖新计划。重复采用同一候选返回已经生成的计划，而不是生成第二份。

服务重启导致未完成识别时，将其标记为“已中断，需手动重试”，不能自动重新请求模型。任务生成的断点恢复与识别请求的恢复是两回事。

## 8. 错误与可操作反馈

| 错误代码 | 原因 | 用户下一步 |
| --- | --- | --- |
| `TASK_LLM_NOT_CONFIGURED` | 主控模型或凭据未配置 | 在模型与供应商页面设置主控 |
| `TASK_LLM_BUSY` | 当前有生成任务或另一次识别 | 等运行完成后重试，不额外排长队 |
| `TASK_LLM_RATE_LIMITED` | 供应商限流 | 等供应商限制解除后主动重试 |
| `TASK_LLM_TIMEOUT` | 本次识别超过请求超时 | 原计划保留；稍后手动重试或编辑原文 |
| `TASK_LLM_INVALID_OUTPUT` | JSON 不完整、字段错误、输出截断 | 缩短或明确指令，再手动重试 |
| `TASK_POLICY_CONFLICT` | 付费降级、禁用强制检查等冲突 | 删除冲突要求或调整合法配置 |
| `TASK_CAPABILITY_UNSUPPORTED` | 当前不能执行的任务/约束 | 明确显示哪一要求不支持，用户修改指令 |
| `TASK_PLAN_CONFLICT` | 基础计划或设置已变化 | 针对最新计划重新识别 |
| `TASK_DB_UNAVAILABLE` | 会话数据库不可用 | 修复 PostgreSQL，不能执行未保存的候选 |

错误提示不只显示 HTTP 状态码。记录请求耗时、模型耗时、校验耗时和错误阶段，不把任务生成时间算进“识别耗时”。

## 10. 验收与测试设计

以下是后续测试清单，本次不执行：

| 测试 | 通过标准 |
| --- | --- |
| 正常本地识别 | 模型调用计数为 0；原有栏目/数量解析不回退 |
| 本地未识别 | 有效原文保存，按钮可用；不自动请求模型 |
| 中文“五篇”、别名、否定语句 | 正确栏目/数量，不补未请求栏目；歧义有具体问题 |
| 点击备用按钮 | 模型调用恰好 1 次；生成/生图/浏览器工具调用为 0 |
| 比较与采用 | 展示变化；采用仅创建新计划，未启动任务 |
| 确认执行 | 当前采用计划只执行一次，幂等检查仍有效 |
| 要求传递 | 速度、主题、平台草稿、角色绑定、评分、同步等在实际工具输入中与计划一致 |
| 明确“至少两条”但执行器不支持 | 不偷偷软化或声称满足；要求调整后才可执行 |
| AI集合稿条目数量 | 不误生成多篇集合稿，不重建已经取消的条目保底 |
| 超时/无效 JSON/限流 | 原计划完整保留，调用次数不自动增加，不切付费供应商 |
| API Key、路径、注入或公开发布请求 | 无泄漏，无权限扩大，无上传/发布副作用 |
| 双击、双标签页、刷新 | 同一请求只有一次模型调用；可恢复候选；过期采用被拒绝 |
| PostgreSQL 故障和重启 | 明确失败/中断，不降级；数据库恢复后手动重试 |
| 断点续跑 | 继续已冻结计划，不再识别，不丢约束或重新生成整批 |
| 桌面/手机与键盘 | 按钮和状态不遮挡内容，焦点/弹层/加载反馈完整 |
| 分发与兼容 | 新克隆的工具快照和实际安装路径一致；旧 GUI/CLI 无自动 LLM 调用 |

成功标准是“识别结果可解释、参数真实落地、操作不越权”，不是所有任意自然语言都能无歧义识别。模型识别耗时报告实际测量的分位数，不在设计阶段承诺固定秒数。
