# 智能体与工作流内存优化设计

日期：2026-10-28。状态：设计及 P0/P1 核心代码已完成，尚未运行测试。原诊断证据保留如下，当前实施范围与未验证项见 [实施记录](2026-10-28-memory-optimization-implementation.md)。

## 1. 目标与边界

降低独立智能体启动后的常驻内存、生成期间的瞬时峰值，以及任务结束后的残留占用，同时保持生成速度、业务完整性和断点续跑能力。

- 智能体继续独立安装于 `E:/AI/codex/redbook_agent`，自带工具位于 `tools/redbook_tools`；工作流继续独立运行于 `E:/AI/codex/redbook_workflow`。
- PostgreSQL/pgvector、384 维嵌入模型、新闻真实性/时效性审查、平台保存回执与不确定结果核对不降级。
- 生成记录、原始信源、草稿、模型配置、参考图库、项目文档全部保留。内存释放不等于删除历史文件。
- 不修改 CC Switch、Codex、Claude Code、默认浏览器及其他软件的任务、账号或服务；只管理项目明确拥有的进程。
- 不增加 Redis、常驻模型服务器、新数据库或 Rust 重写。优先修改已有模块，不重复建设任务队列、浏览器批处理和 MCP 生命周期。
- 本文中的参数和容量目标均为拟实施值，不是当前已生效配置或实测优化成果。

### 2.3 图谱与结论边界

GitNexus 绑定 `redbook_auto_agent` 与 `auto_redbook` 两个仓库；索引时间为 2026-10-24，智能体 HEAD 与索引记录相同。已有未提交修改保留；有关行为另以当前源码与本地依赖源码核对，未在低内存环境下重建大型索引。

`get_embedding_model` 上游包含索引、prepare_chunks 和知识库检索；`start_rsshub_if_needed` 上游包含 CLI create/auto。上述两个 impact 的图谱评级均为 LOW，但仍触及 RAG/AI 讯息公共链路，实施时按业务中风险回归。startup/release 等动态调用存在图谱下界，不将缺失调用者解释为无依赖。

结论：已确认数个重复分配、长期保留和回收缺口；尚不能证明哪一项是用户此前高内存的首因，也不能宣称已经确认内存泄漏。必须增加阶段内存曲线后排序。

## 3. 总体方案

```text
React 页面：按页加载、摘要/事件增量、后台降频
        |
轻量 API：有界任务摘要、按需详情、已有 PostgreSQL 持久化
        |
现有任务执行进程：受控并发、产物及时落盘、仅持有在途数据
        |-- 知识库：单进程嵌入 + 小批次 + 增量摄入
        |-- 图片：先取得执行槽，后读取/编码/解码，及时释放缓冲
        |-- 平台：沿用专用 profile + 串行批量保存 + 回读
        `-- RSSHub/WorldMonitor/MCP：按需借用或启动，按所有权释放
```

低内存优化和 `speed/balanced` 是正交维度；不新增互斥的第三种工作流。资源压力只限制新操作的准入，不能强杀进行中的图片请求和平台写入。

## 4. P0：优先修改现有模块

### 4.1 嵌入与导入

1. 调整 `src.knowledge` 导出、服务和 store 的导入边界，使健康检查、配置、草稿列表、普通聊天页面不导入 FastEmbed/ONNXRuntime。维持原公开接口的兼容性，不把整个后端重写。
2. CPU 嵌入默认 `parallel=None`，使用现有 ONNX 两线程；不使用 0，因为当前依赖把 0 解释为全部 CPU 核心。
3. 推理批默认 16，压力时 8；索引读取批默认 32 篇，并设置总 token/chunk 上界。单个长文档继续分块，不能让一篇超长文档绕过批次限制。
4. 模型初始化使用单飞锁，防止同一进程两个查询同时构造 `_MODEL`。锁不覆盖后续网络和数据库事务。
5. 模型文件使用固定 1 MiB 缓冲流式 SHA-256 校验，仍验证全部文件与原 manifest，不省略完整性检查。
6. `prepare_chunks` 分组生成和提交，不同时保存一整轮所有文本、向量和重复数组；数据库继续写入相同模型 ID、384 维向量及 chunk_version。
7. 不通过频繁 `gc.collect()`、清空 Windows 工作集、关闭交换文件伪装内存下降；ONNX 原生分配不保证随 Python 引用删除立即归还系统。

第一阶段仍使用已有进程内模型接口，不直接增加常驻嵌入服务。若完成上述改造后，API 首次检索后的保留量/双份模型仍超出验收目标，再执行第 7 节的隔离方案。

### 4.2 摄入与历史任务

- 摄入复用已有 `iter_posts`，不经 `list_posts` 全量列表。每批转换并 upsert 32 篇，批次提交后释放对象，累计 inserted/updated/unchanged 计数。
- 保留 content_hash 幂等和历史版本；失败批次可重试。不能因分页跳过旧帖，不能将小批次提交宣称为全量任务原子成功。
- 首次全量导入仍完整遍历；后续优先采用已持久化的摄入清单和内容版本。新增/更改路径作为增量，周期低优先级完整核对，处理移动、损坏和时间戳变化；不能仅凭 mtime 跳过必要校验。
- Workbench 只常驻活动任务和最近 50 个终态摘要，不在启动时保留所有历史 events。较老任务按 ID 从现有 journal 读取，列表游标分页，原文件不删除。
- 任务详情缓存拟上限 8 项、合计序列化体积 4 MiB；活动任务不可被淘汰或中途丢失持久化责任，完成后释放其进程/环境/大对象引用。序列化体积只是缓存限额代理，另采实际进程内存。
- 历史任务恢复保留原中断状态核对规则。分批扫描未终结 journal，不能只恢复最近 50 项，也不能自动重传不确定草稿。

### 4.3 图片缓冲

- 复用 `ModelWorkQueues`、`_image_slot` 和共享请求键；等待队列仅保留路径与请求描述，取得槽后才读取参考图、base64 编码。
- 移除 chunks 与 join 的双份大缓冲；采用单个有界接收缓冲或受控 E 盘临时文件，明确 JSON 解析仍有额外分配，不把 `json.load` 误当作流式 JSON 解析。
- 完成解析后立即释放原始响应和 JSON 大字符串；分块解码、hash/复制使用已有成熟接口。若需新增增量 JSON 库，必须先证明标准库方案仍超标并另行评审，不能手写脆弱 JSON 字符串切割器。
- 图片转换/预览只保留当次必要分辨率，中间 PIL 对象及时关闭；不为节省内存改变已保存最终图片质量。
- 保持现有响应大小、参考图大小、请求状态和文件校验契约；不默默降低到会拒绝正常图片的响应上限。
- 不改变 CC Switch 订阅校验、账号选择、不确定请求不重复提交、禁止付费 API 回退等边界。

## 5. P1：生命周期与界面常驻量

### 5.1 按需服务所有权

优先为 RSSHub 增加可释放的运行租约，并保留原 bool 接口兼容。WorldMonitor 和 MCP 使用已有 owner/finally/idle 结构，补齐异常路径即可。共同遵守：

| 场景 | 行为 |
| --- | --- |
| 借用已存在的用户/其他任务服务 | 记录 borrowed，不赋予停止权限 |
| 当前任务启动的服务 | 记录 owner、PID、启动时间、可执行文件、端口及租约 |
| 最后使用者释放 | RSSHub/WorldMonitor 拟宽限 30 秒后关闭自身进程树；压力时可跳过宽限，不能中断有效请求 |
| MCP | 保留现有 60 秒空闲关闭；正常任务退出必须 close，不重复建设会话池 |
| 超时、取消、异常 | finally 释放租约；父进程异常退出后，仅在身份核验通过且无有效租约时清理孤儿 |
| 工作流与智能体同时借用 | 在共享 runtime 下协调服务租约，跨进程互斥；不能因其中一个任务结束而关闭另一个仍在使用的服务 |

不得按 `node.exe`、`chrome.exe` 名称批量结束进程；不得仅凭端口或可复用 PID 结束服务。PID 必须连同启动时间、路径和 owner 核对。项目手动浏览器窗口与自动任务争用 profile 时沿用现有提示，不强行关窗。

小红书仍是一批任务一个串行写入会话、完成后关闭；不在等待 LLM/图片时提前开着浏览器。保留审核、回读及 `XHS_WRITE_UNCERTAIN` 处理。全球地图采集/截图完成后释放自有资源，不启动可见 WorldMonitor 页面。

### 5.2 页面与 API

- 首屏只加载当前页必需摘要；连接页、图库、历史任务和草稿详情按需读取，不在聊天首屏同时拉取全量。
- 复用已有运行事件/SSE 接口，但先验证其内部不再为每次增量构造全会话历史；不能只是将原有全量轮询外套一层 SSE。
- 活跃任务进度增量 1-2 秒；无活动的终态只在新指令/手动刷新时更新；后台标签页降至 15 秒或停用非必要订阅，返回前台补齐。
- 对话消息与技术日志分页，最近消息默认 50 条；展开技术日志才读取/序列化。限制内存窗口不删除历史对话，也不改变模型上下文的真实压缩逻辑。
- 对话/goal/context 分别使用 revision 或 ETag，未变更不重传；前后端一并兼容，旧接口保留迁移期，不破坏编辑计划和确认事务。
- 图片使用缩略图和懒加载，不将原图 base64 放入 React 长期状态；离开页面时撤销临时 object URL、订阅与图片解码引用。

### 5.3 PostgreSQL

先保留 shared_buffers、fsync、WAL 与 synchronous_commit。验证 SHOW、pg_stat_activity 后，拟将 API 应用池 max=4、普通任务池 max=2、迁移池 max=1，空闲连接 min=0，并显式关闭已完成进程/迁移角色的池；需要调整现有 max 至少为 2 的约束，不能仅设置无效环境变量。

连接池按进程/角色合计核算，保留现有池复用，避免每请求新建池。只有确认空闲连接过多才实施；不依靠任意降低 max_connections 造成任务锁死。数据库异常依旧明确报错，不降级到内存或文件库。

## 6. 低内存准入与运行可见性

在已有 `PerformancePolicy`、请求预算、模型队列和 RunContext 上增加轻量观测/准入，不新增并行调度器。拟使用 Windows 标准接口采样；跨平台实现先检查现有依赖，不自动安装系统工具。

| 状态 | 初始阈值 | 准入策略 |
| --- | --- | --- |
| 正常 | 可用内存至少 2 GiB，且无持续压力 | 保留供应商并发上限；CC Switch 保留自身 1/2 槽设置 |
| 紧张 | 连续 3 次采样低于 1.5 GiB，或不足总量 10% | 新图片请求一次 1 个，嵌入批降到 8，暂停非必要预取/索引预热；远端 LLM 仅在本地缓冲确有压力时减并发 |
| 严重 | 连续 3 次低于 0.75 GiB，或不足总量 5% | 不再启动新浏览器/模型进程/大图解码；进入资源等待，保留并落盘已完成产物，安全完成在途写入 |
| 恢复 | 连续 30 秒高于 2 GiB | 缓慢恢复新任务准入，避免并发抖动 |

阈值是待测起点，需按阶段启动成本增加预留量。采样建议运行期 5 秒、空闲 30 秒；未知/采样失败时使用保守并发，不把未知当作零占用，也不永久阻塞任务。

- 不减少用户目标条数，不关闭事实审查，不设置新的共享总耗时预算，不因压力自动整批重跑。
- 内存等待状态必须显示原因、等待时长、完成/待完成数，并提供暂停/继续；不能只显示“运行中”或假完成。
- 当前请求已提交但结果未知时保留原幂等/不确定状态，不因内存重试重复生图或上传。
- 记录总耗时、资源等待耗时、实际工作耗时，不能把等待从端到端统计中隐藏。
- 记录 stage、PID/父 PID/owner、工作集、Private Bytes、系统可用内存、活动模型/浏览器/Node 数、队列在途数量、缓存大小和运行 ID，不记录命令行凭据、正文、Cookie、OAuth 或 base64。
- 采样日志写入 `redbook_runtime/data/logs/resources/<日期>/`，每文件拟上限 5 MiB、最多 3 个滚动分片；业务生成记录与原始证据不参与自动清理。

## 7. P2：仅在 P0/P1 仍不达标时隔离嵌入

若 API 做过一次向量查询后长期保留模型内存，且轻量优化仍不达标，增加一个按需、短生命周期知识库执行进程，而非常驻服务：

1. 同一 runtime/模型版本在活跃租约期间只保有一个执行进程，W/A 都可使用；每套程序仍带齐独立启动它所需的工具。
2. 复用既有知识库检索和索引接口，只替换执行边界；参数为查询/文档引用，结果为有限 hits/计数，不通过 IPC 来回复制全知识库。
3. 查询优先于后台摄入；操作单飞、有界队列，空闲 60 秒且无有效请求时退出。内存压力时在安全边界提前退出。
4. 在 PostgreSQL 保留已提交分块和版本；进程退出释放 ONNX 原生内存。异常后只重放未完成操作，不重新生成新闻。
5. 内部通信仅本机、带会话校验，不创建外网服务；worker 本身不允许回落到其他嵌入模型或数据库。
6. 必须比较冷启动代价、API 响应时间与峰值收益；收益不足则不引入该模块。不得直接以该方案替代第 4 节的低成本修复。

## 9. 容量与验证标准

这些是待测目标，不是本次承诺或已取得的节省量：

| 场景 | 初始目标 |
| --- | --- |
| 仅启动 API/聊天，尚未向量检索 | API Private Bytes 不超过 350 MiB，且无 ONNX 权重实例 |
| 空闲 10 分钟 | 项目自有应用进程总量不随历史任务数线性增长；不必要的 RSSHub/WorldMonitor/浏览器为 0 |
| 相同输入与数据完成生成 | 自有进程峰值 Private Bytes 至少降低 30%，并另报告工作集/共享内存，不能混用口径 |
| 正常余量下的效率 | 同条件端到端中位耗时退化不超过 10%；外部网络/供应商等待另列，不混称代码收益 |
| 10 条新闻 + 1 条 AI + 1 条地图 | 总自有应用进程峰值暂以 2.5 GiB 为容量参考，不含共享服务和数据库共享页重复计数；基线超出时先解释差额再定最终阈值 |
| 连续 20 轮轻量任务 | 预热后空闲保留量不超过基线加 10% 或 50 MiB 中较大者；无随轮次持续上升趋势 |
| 任务结束 60 秒后 | 自有临时服务和句柄完成释放；借用的用户服务仍运行；已完成稿件不丢失 |

原生分配器可能使单进程保留高水位，不能仅因其没有回到冷启动值就判泄漏；需同时检查多轮趋势、对象/句柄、活跃模型数和执行进程退出后的系统变化。真实验收按随附测试计划实施。
