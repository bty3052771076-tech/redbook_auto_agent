# 新闻生成与审核流程提速设计

日期：2026-10-10。状态：设计待评审，未实现、未进行新模型或平台测试。

## 1. 目标、范围与决定

目标是缩短“10 条每日新闻 + 1 篇每日 AI 讯息”的首次完整交付时间，同时保持新闻可核验、近期、去重、内容完整和断点恢复能力。优化对象是独立智能体及其内置工作流；独立工作流使用同一行为契约，但继续独立部署和人工运行。

本次只交付设计和实施测试计划，不生成内容、不操作平台、不修改业务代码、不提交 Git。设计采用 brainstorming、writing-plans、performance-profiling 的流程。

方案比较：

| 方案 | 优点 | 主要问题 | 决定 |
| --- | --- | --- | --- |
| 全面 Rust 重写 | 可降低本地计算开销 | 尚无 CPU 热点证据；不减少模型等待和无效重写；需重验全部接口 | 不采用 |
| 仅提高并发 | 小范围改动 | 当前已有并发；会放大错误请求、账户限流和配置串扰 | 不单独采用 |
| 分离审核、定向修复、持久化流水线 | 直接减少无效工作，可逐阶段验证和回滚 | 涉及核心生成、恢复与交付契约 | 采用，先减少返工，再提高重叠执行程度 |

不新增 Redis、Celery 或另一套智能体框架。继续使用现有 Python、LangGraph、PostgreSQL、线程池和 Playwright。后续只有测得明确 CPU 热点，才另行评估局部原生实现。

## 3. 不可放宽的边界

1. 用户确认的数量、关键词、软偏好、必须满足项、日期窗口和交付方式保持冻结。偏好不变成硬配额，硬要求不足不得冒报完整完成。
2. 普通新闻内容目标 150–220 字，复杂事件沿用现有有证据的复杂性判定、最多 300 字；评价目标 20–40 字、最多 40 字。按现有非空白字符计数。材料不足不凑字，超长重新总结，不截断句子。
3. 每日 AI 沿用北京时间发布当天和前一天的最终窗口。新闻沿用当前确认的回溯规则，不因提速擅自拓宽。事件发生时间、消息发布时间、抓取时间分别记录。
4. 图片评分模式 `advisory/required` 不改变含义。参考分不阻止交付、不因低分重画；图片损坏、明确事实冲突不能伪装成参考分放行。
5. 所有平台操作使用指定 profile，同一 profile 同时只能有一个平台会话和一个写入者。禁止并行上传、盲点发布、绕过验证码、平台限制或结果不确定状态。
6. 订阅充足不等于无限并发；不主动同步额度，不静默换付费 API，也不在性能优化中变更模型绑定。
7. 智能体 PostgreSQL 保持必需，不降级为 SQLite/内存。两套程序的凭据和运行记录不上传 Git、不安装到 C 盘、不在仓库根目录堆放日志。
8. 不恢复 120 分钟整批截止或跨栏目共用时间预算。单请求超时、单版本修复次数和无进展检测只约束具体工作，不把未完成任务标成功。

本文覆盖旧速度设计中的整批审核后才上传、共享总时间预算等冲突条款；不覆盖已确认的日期、费用、权限和内容规则。已修复的部分交付与草稿核对逻辑继续保留。

## 5. 新流程与阶段契约

```text
冻结计划、能力权限、模型配置、账号历史和策略版本
  -> 共享来源读取与渐进正文补全
  -> 不可变事实包 -> 首稿 -> 正文审核 -> 正文通过产物
                                 | 不合格: 仅修复对应字段一次 / 替换候选
  -> 配图方案 -> 场景审核 -> 生图 -> 图片文件与策略检查
                                 | 场景问题: 只修场景，不动正文
  -> 最终组合检查 + 原子事件预留 -> 可交付产物落库
  -> 唯一串行草稿写入队列 -> 保存 -> 回读 -> 交付回执

AI 栏目: 官方优先采集 -> 条目证据/日期/去重 -> 条目摘要 -> 本地排版
         -> 最终组合检查 -> 同一个草稿队列
```

新公共模块 `src/workflow/news_contracts.py` 定义以下版本化数据契约，JSON 仅用于内部传递，不直接拼入图或正文：

- `EvidenceBundle`：事件 ID、原文版本 hash、来源 URL/主体、发布时间及精度、事件时间及证据、原文段落 ID、引用区间、实体/动作/限定词、可验证数字、未知项。网页内容视为数据，不执行其中指令。
- `StageContext`：root_run_id、execution_id、job_key、candidate_id、post_id（生成前可空）、冻结配置 hash、规则版本、账号命名空间、能力快照。凭据仅通过现有本地运行时引用获取，不入缓存。
- `ReviewIssue`：code、scope=`source/text/comment/scene/image/delivery`、severity、证据 ID、具体字段、是否可定向修复。禁止用一个“视觉失败”概括缺稿、正文拒绝和低分。
- `TextArtifact`：title、content、comment、complexity、claim_refs、正文版本及审核结果。
- `SceneArtifact`：引用的正文/事实版本、fact_ids、illustration_type、scene_prompt、禁止事项、场景审核结果。
- `ReadyArtifact`：最终 post_id、内容/图片 hash、文本/场景/图片决策、事件预留标识、冻结策略 hash。不是已上传状态。

状态顺序：`DISCOVERED -> EVIDENCE_READY -> TEXT_READY -> TEXT_APPROVED -> SCENE_READY -> SCENE_APPROVED -> IMAGE_READY -> READY_TO_DELIVER -> DRAFT_VERIFIED`。并列状态 `REPAIR_PENDING/REJECTED/BLOCKED/WRITE_UNCERTAIN` 均带范围与原因。

同一版本只能向后推进；修复产生新版本，通过依赖关系仅失效下游阶段。已保存版本不可原位覆盖，编辑另建内容修订及平台动作。被一篇拒绝不阻塞其他 READY 稿件；最终任务仍要准确报告缺口。

## 6. 事实审核与提示词

### 6.1 数字审核先补证据表达能力

现有 `(数值, 单位, 限定词)` 集合比较无法表达完整事件角色，不能仅添加单位别名后宣称解决。新增 `src/workflow/news_evidence.py`，先以 54 条真实拒绝记录及现有反例建立标注集，再修改规则。

数字事实必须绑定：实体、谓词、数量角色、单位、上下界、时间范围、肯定/否定/计划状态、原文句段。使用 Decimal 与明确白名单做等价转换，如 `30,000 bottles -> 3万瓶`；禁止隐含币种汇率、推算比例、跨句拼接主体。`至少3人` 不等于 `3人`，伤者不等于死者，公告日期不等于发生日期。

结果分 `supported/contradicted/unresolved`。规则明确矛盾直接退回，不能由 LLM 投票覆盖。未识别表达可使用一次定向语义核对，请求仅带疑点和相关原文段；模型必须返回存在于快照中的引用，服务端检查引用与实体、动作、数量关系。模型“通过”不是充分证据，仍无法核验则修复/替换。不能把所有未识别数字默认通过，也不能用删完整句子留下残稿来规避。

事实包优先由已采正文和确定性抽取构建；不为每篇机械增加一次全文 LLM 提取。首稿一次返回正文、事实引用和初步场景，内部引用必须能回到原文，不接受自引用。

### 6.2 首稿提示词契约

```text
只根据 EvidenceBundle 写一件事。先确定主体、动作、对象、结果/当前状态，
再保留理解事件必需的原因、回应及限制。未知信息不补齐。
普通内容150–220字，优先180–200字；评价20–40字，优先25–30字。
复杂事件必须提供现有规则可验证的复杂性证据，最多300字。
标题写明具体主体与发生的动作，不用“几位大佬”“披露变化”代替内容。
保留原文中的至少、约、计划、否认和来源归因。数字只取对应事件的证据。
返回结构化字段与 claim_refs；不输出HTML，不把内部引用、JSON字段写入展示正文。
评价只说明一个具体影响或信息边界，不复述全部事实，不用空泛口号。
场景是概念插画建议，优先一个明确主体和一个已证实动作/状态，尽量无文字。
```

后端复用现有简体中文、编码、完整句、长度和事实检查。`max_tokens` 继续保证足够容纳结构化输出，不靠截断限制中文篇幅；只有实际 `finish_reason=length` 才进入截断诊断。

### 6.3 定向修复矩阵

| 问题 | 允许修改 | 必须保持 | 每候选版本上限 |
| --- | --- | --- | ---: |
| 数字、主事件、来源归因、正文长度 | title/content/claim_refs 中出错字段，必要时同时修相关 comment | 原文快照、事实边界 | 文本修复共 1 次 |
| 只有评价超长或空泛 | comment | title/content/claim_refs 字节 hash | 使用同一个文本修复额度 |
| 仅场景未核验或构图复杂 | SceneArtifact | 已通过正文和图片评分策略 | 场景修复 1 次 |
| 来源不足/过期/重复 | 换候选或补真实来源 | 不由模型编造补足 | 同版本不重复请求 |
| 图片低分，参考模式 | 无需改写/重画 | 真实分数及原因 | 0 次低分补偿 |
| 图片低分，强制模式 | 按既有策略生成第二张，保留两张及评分 | 正文不重写，总计最多 2 张 | 第二张仍低则选较高分供审；仍不满足强制门禁不能声称合格 |

定向修复提示词使用 `scope + issues + allowed_fields + immutable_hashes + evidence_spans`。返回只包含允许字段的 patch；应用前核对基版本和不可变 hash，应用后复审变更项及其依赖。模型擅改无关字段时拒绝 patch，不用整稿覆盖。

正文审核通过后优先使用首稿已有场景，通过则零额外请求。场景修复无效时，可生成事实包支持的明确“概念示意”构图，再走同一场景检查；不能把计划画成已经发生的现场，不能用纯装饰图冒充事件配图。确定性方案也失败时只拒绝该候选。

## 7. 缓存、持久化与断点

复用 `KnowledgeStore` 连接池和迁移权限，新增 `src/workflow/stage_store.py`，不在 HTTP/LLM 请求期间持有数据库事务。

| 存储 | 职责与关键字段 |
| --- | --- |
| 现有 knowledge.documents/document_versions | 可追溯材料与内容版本，复用既有权限命名空间 |
| 新 agent.news_stage_cache | 不可变阶段产物；主键 `(namespace, stage, input_hash, contract_version)`；output_hash、payload、created_at、expires_at；同键不得后写覆盖不同产物 |
| 新 agent.news_work_items | 可恢复调度；主键 `(root_run_id, job_key, candidate_id, stage, input_hash)`；status、artifact_ref、attempt_count、lease_owner、lease_until、lease_epoch、next_attempt_at、last_error、version |
| 新 agent.model_request_leases | 跨进程模型容量；主键 `(capacity_group, request_id)`；modality、owner、epoch、status、dispatched_at、request_deadline_at、lease_until、provider_request_id；状态区分排队、在途、结果未知、已结束 |
| 现有 agent.task_artifacts | 已有 post 的持久化真相，不用新调度表复制整篇并形成第二个主存储 |
| 现有 DeliveryStateStore | 外部提交动作与回执真相；队列完成不等于已保存 |

缓存键必须包括源快照 hash、提示词/规则版本、冻结选择条件、模型 ID/连接配置修订、语言及账户命名空间。审核事实结果和使用资格分开缓存：命中正文审核也要重新检查当前日期、事件历史、权限和用户要求。视觉观察可复用，切换评分策略须重新计算决策，不重写原分数。

原文使用 ETag/Last-Modified 时，304 复用对应内容并更新检查时间，不表示没有消息。拟定来源刷新 TTL：重点官方源 15 分钟、普通源 30 分钟；日期资格不跟随 TTL 延期。暂时失败负缓存默认 60 秒，429 尊重 Retry-After；真正内容拒绝绑定原文/规则 hash，新证据或新规则可重新评估。

相同请求使用 single-flight，失败不能永久缓存成“无新闻”。原文、首稿、修复稿、场景、图片分别复用；只有 comment 改变不得重新抓取和写正文，但影响版面或视觉核验时应失效相应下游。

调度领取与状态提交采用短事务 CAS，租约续期和 fencing epoch 防止过期工作者覆盖新结果。图片等大文件先在同卷临时目录原子落地并校验 hash，再提交引用；崩溃留下的孤立文件记录为待核对，不删除原始生成记录。只恢复未完成阶段，已交付稿永不自动重传。第三方生图/写入超时且结果未知时保存 request_id 和未知状态，能查询则查询；不能查询时不得声称 exactly-once 或盲目重复计费。

重启后对尚未交付产物重查日期与发布历史。跨日时同时检查原确认日期窗口与实际交付日的新鲜度，过期稿保留并报告，不能仅把展示日期改成今天。数据库不可用时保留已落盘证据，停止新增外部副作用并报明确错误；不可静默换本地数据库继续写平台。

新增 `src/workflow/news_execution.py` 管理运行级调度，LangGraph 仍负责计划、恢复及汇总；工作线程通过消息/产物回传，由单一协调者更新图状态，禁止两个栏目直接修改同一个 AgentState。

- 初始两个栏目生产者：每日新闻和每日 AI。MiniMax 写稿、控制器、定向语义检查等共用账户/连接组最多 5 个在途槽位；AI 有待办时采用加权轮询新闻:AI=3:1，空闲可借槽，不把已有请求强制中断。
- 生图沿用独立最多 2 个在途槽位。若提供商声明跨模态总上限，还须叠加账户总限流。通过 PostgreSQL 租约协调同一账户在 agent/工作流进程中的上限，不存储原始 API-key。
- 容量组使用非敏感 `quota_group_id`，同一账户的多个连接别名绑定同组；未明确分组时保守按提供商和规范化端点共享，不能把无法识别的账户默认当成独立额度。组上限取账户配置与活跃计划限制中的最严值。新 `model_capacity.py` 封装租约，不把数据库锁细节塞进模型适配器。
- 在途请求的 worker 租约失联，不能立即把远端仍可能执行的请求当作已结束并补槽。先等待已有请求终止证据/适配器最迟请求边界，保留 unknown 标记；重发计费请求另需结果核对。无法确认远端状态时只报告本地派发上限，不声称证明了远端绝对并发数。
- 429 按响应退避、暂时减小窗口，连续成功后逐步恢复到配置上限；不假设订阅不会限流，不凭次数判定额度用尽。
- 材料抓取初始总并发 4、单 host 1；优先供给正文就绪项。单请求沿用适配器有界超时，不把某个慢源当成整批屏障。
- 正文通过后在生图前原子预留事件与交付槽位；最终入队再检查历史增量。最多保留 2 篇已审正文替补，不为未获目标槽位的备选提前生图。到达目标后不再派发新候选，收回未启动工作，保留已返回结果。
- 同 profile 的读取、同步、上传、回读统一占用平台会话所有权。已启动保存不能被同步操作抢占；等待不会锁住模型线程。
- 草稿消费者位于专用线程，整个 Playwright sync 会话只在该线程创建、使用、关闭。复用一个健康会话串行保存，不能把 page/context 跨线程传递。写入前校验账号、profile 和内容版本；手动窗口占用时等待用户处理，不切默认 profile。
- 原有本地动作账本有进程内 RLock，不能把它视为跨进程锁。两程序共用 runtime 时增加 PostgreSQL profile 会话锁，账号有多个 profile 时再叠加账号写锁，锁必须覆盖账本 prepare/提交/观察/回执落地。
- 统一按“账号锁，再 profile 锁”的顺序申请；等待平台锁不占模型槽。每个外部写入前验证锁连接仍有效，丢锁立即停止新写入，当前不可判定动作转入核对流程。
- READY 先持久化再排队；消费者启动及每次保存后扫描持久化待办，内存通知丢失也能续跑。外部保存成功、本地回执未提交的崩溃窗口仍由原有只读 reconciliation 处理。

重要前置：`temporary_environment` 当前修改 `os.environ`。并发路径不得继续在任务中临时覆盖模型/代理/评分环境；须先把冻结配置显式传入适配器，或在不得不使用旧适配器时串行隔离该段。未通过两栏目配置隔离测试前，跨栏目并发保持关闭，不能仅包一层 ThreadPoolExecutor。

## 9. 每日 AI 专项

复用已有 collect/generate/rank，不重写成另一套采集器。新闻和 AI 可共享原文获取，但不能共享同一套选题资格结果。

1. 官方模型发布和重要厂商动态优先；聚合站、AIHOT、社交媒体作为发现线索，保留可核验原始出处和日期。
2. 先按实际事件、厂商、产品版本和动作去重，再做模型摘要。相同发布的多家转载不算多源独立事件。
3. 候选按批最多 6 个做结构化摘要，要求逐条 item_id 和证据引用；一条摘要失败只定向修该条一次，不重写整篇简报。条目可放入同批请求，但不能串用事实。
4. 摘要必须回答“谁发布了什么、具体变化、何时/如何可用、限制条件”。无具体变化、日常 GitHub 审查错误和过期旧闻不得为凑数量入选。
5. “生成 1 篇”不等于“只找 1 条”。按冻结的条目数/来源多样性策略选择有效事件，保留全部合格条目供最终排版；分页只受真实平台图片/正文限制，不降低核验覆盖以达时间目标。
6. 本地排版继续处理 HTML 清洗、内部 JSON 隔离、标题分行和文本溢出。官方源超时记覆盖未知，不伪称当天无发布；备用可核验来源命中后不等待无关慢源，但重要未核实线索与覆盖缺口必须显示。

## 10. 计时、界面及失败语义

扩展现有 telemetry，不新增重量级监控平台。每个 span 带 root_run_id、execution_id、job_key、candidate/post_id、stage、attempt、parent_span_id、provider/model、queue_ms、service_ms、outcome、cache_hit、input/output_hash；只记录 token 数字，不记录授权头、cookie、密钥或完整提示词到 UI 日志。

以 monotonic 计算本次执行间隔，以 UTC 起止时间关联跨执行。明确三个口径：首次启动至全部回读的用户等待；各次活跃执行区间之并集；各阶段工作时长。并行阶段时长不能简单相加当端到端时长。

界面及 CLI 同时显示：正文已通过、配图已就绪、草稿已确认、待修复、已淘汰、重试中；每栏按 post_id 去重。另显示首篇可交付、首篇平台确认、全部确认用时，以及模型请求数、重复工作节省数和主等待原因。未知预计时间显示未知，不用固定百分比承诺剩余时长。

内容错误只隔离单篇；平台未知结果、登录/验证码/限制暂停该账户的写入，其他合法的本地生成可继续完成。额度耗尽暂停相应模型队列；网络暂错遵循退避，不整批重置。连续 3 次无新材料、无阶段进展且仍不足时记录明确缺口，等待新证据或用户调整，不无限轰炸、不编造凑数。

知识库的交付状态与去重占位必须同步提交；全文嵌入等非交付关键工作写持久化后台待办，失败显示“索引待补齐”，不能使已回读草稿倒退为上传失败，也不能丢失待办。

## 11. 验收目标与分期

性能目标是工程验收目标，不是当前实测结果或停止预算：

- 在模型、材料、策略和缓存条件一致的受控配对测试中，总活跃墙钟时间中位数降低至少 35%，交付完整率不下降；失败样本单独列出，不从统计中删掉。
- 性能结论至少需要 3 组同条件完整成功的配对样本，并同时列出全部尝试的失败率和缺失产出；样本不足写“无法判断”，不得以只生成部分稿件的运行时间替代。
- 一次 10+1 的目标区间为 30–40 分钟，包含串行保存与逐篇回读，仅用于容量目标；需用健康外部服务、相同账号同步方式验收，不承诺服务异常仍满足。
- 与本次材料固定回放对比，文本模型调用减少至少 50% 为目标；218 条日志仅作线索，正式请求计数包含失败、重试、控制器及审核并按 request_id 去重。
- 合格事实包的新闻首稿通过率目标至少 70%；图像首图真实审核通过率单独记录，不把关闭门禁算作通过。
- 仅场景修复导致正文重写次数为 0；已通过且输入未变的阶段在续跑时额外模型调用为 0；同 profile 并发写入最大值为 1；重复草稿为 0。
- 来源、日期、数字、HTML/JSON泄漏、断句与事实完整性的金标反例不得回归。性能合格而内容退步，整体验收失败。

阶段 A：计时与金标、事实核验、定向修复、阶段缓存；保持现有栏目执行顺序，先证明返工下降。

阶段 B：冻结配置隔离、共享槽位、逐篇流水线、专用串行消费者；再开放两栏目并发。参考图片评分在两阶段均遵循原用户选择。

新增冻结字段 `generation_pipeline_version=legacy|staged_v2`，默认先保持 legacy。新任务通过受控灰度启用 staged_v2；旧检查点保留原版本，显式迁移只复用有完整依赖证据的阶段。回滚仅影响新任务调度，不删除已保存产物/动作账本，不自动把 v2 检查点送进 legacy 重跑。

实施步骤、测试命令和故障注入见 [实施与测试计划](2026-10-10-news-generation-review-performance-implementation-test-plan.md)。
