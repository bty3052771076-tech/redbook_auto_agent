## 原因与修复

### 生图拒绝被误记为不确定

旧适配器在 POST 后把 HTTP 400 当作结果不确定，并丢弃错误正文。相同提示词及双图哈希进入跨稿件保护记录，后续尝试只能再次撞到该记录。

代理使用记录确认原请求为 HTTP 400、`payload-rejected`。保留记录副本后进行一次诊断，得到 `moderation_blocked`、`safety_violations=[sexual]`。这是服务端对该组编辑素材的拒绝，不是额度耗尽；不通过反复提交或隐瞒内容规避审核。

修复：

1. 明确的 400/403/413/415/422 记录为 rejected；网络中断、真正超时与不确定结果仍保留 uncertain 保护。
2. 本地与共享记录都阻止对相同被拒请求的盲目重提。历史 HTTP 400 记录读取时正确分类，但不会自动解锁重试。
3. 限量读取错误响应，保存经过脱敏的 code/type/param/message，并在异常中显示可操作原因。
4. 新增普通文本供应商不再误拦当前图片路由。仅允许经固定版本路由审查确认不参与图片请求的 openai-chat 配置；仍拒绝图片自定义路由、OpenAI API-key 和 Google Antigravity 兜底，继续验证源码哈希、版本与配置一致性。

### 智能体没有区分等待与不可原样重试

无时间总预算本身不是故障。问题是已知永久拒绝、未核实的副作用，以及连续无新材料，都进入普通轮转恢复。

修复：明确的图片拒绝或待核实提交只阻塞对应任务，保留其他任务进度；相同 AI 资讯材料不足连续出现三次，标为 `SOURCE_REFRESH_REQUIRED`，等待补充或修正材料后显式续跑。覆盖英文材料不足和中文完整性校验错误。普通暂时错误继续原有重试策略，不重新加入整批时间预算。

### GitHub 单版本重复入选

第一次恢复又暴露出同一版本页的原始标题和中文研究标题被计为两条。旧规则为保留同一个官网更新日志页面内的多个独立事件，把共享 URL 附加标题后再去重，错误地应用到了 GitHub 单版本页面。模型随后出现少写或空条目，兜底英文也未通过中文质量检查。

修复：GitHub `releases/tag/` 页面按版本 URL 合并，不按不同标题拆开；版本标题限制在仓库内匹配，不用 `topic:v2` 这类粗粒度主题合并不同版本。官网多事件更新日志的原有行为不变。回归覆盖同版本不同标题、不同版本、不同仓库相同版本号。
